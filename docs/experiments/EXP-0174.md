# EXP-0174 — Decode W4U8 Gate/Up intra-command pair publication

## Decision and purpose

EXP-0173 is an evidence-valid, promotion-eligible decode candidate and is the
provisional source parent for the continuing user-authorized decode loop. Its
largest remaining module is Gate/Up plus SwiGLU at about 16.83 ms/token.
Earlier EXP-0083 showed that simply widening Gate/Up HMX batches from eight to
sixteen is slower: HMX-ready and expanded-slot waits fell, but the HMX owner
published no completed Gate/Up pair until the entire wider command returned,
increasing producer/pair-slot wait about seventeen fold. This experiment tests
a new mechanism that directly addresses that rejected mechanism rather than
repeating the batch-width search.

## Bounded cells

One binary exposes three M=1 decode-only cells:

* the exact EXP-0173 batch-eight post-command-publication control;
* batch eight with per-pair publication and expanded-slot release from inside
  the HMX batch loop;
* batch sixteen with the same per-pair publication and release.

After every odd Gate/Up output tile is stored, the HMX worker must immediately
make that completed pair available to the existing persistent HVX workers for
SwiGLU. Each expanded-weight slot must be returned as soon as HMX has consumed
that output, not after the whole coarse command. The existing ring-sixteen and
eight pair slots remain unchanged. Prefill remains on the EXP-0173 path.

The W4 stream, qparams, HMX arithmetic and output order, three expansion
workers, SwiGLU LUT mathematics, Down path, all other Transformer/cache stages,
LM-head batch-sixteen candidate, token feedback, and public DDR contract are
immutable.

## Gates and evidence

Static and audit evidence must prove the requested batch/publication mode,
per-output expanded-slot releases, one publication and one consumption for
each Gate/Up pair, byte-exact stage/token/code/hash results, exact 8 MiB VTCM,
one FastRPC/pass, no QNN, zero timed intermediate/full-logit DDR, zero
spill/fill and zero ledger residual.

A bounded rotated gate compares all three cells on continuous real-token
decode. A candidate advances only if Gate/Up wall and complete Host wall are
both lower than the post-command batch-eight control. If both inline cells
pass, select direct complete decode throughput, using Gate/Up time and waits to
explain the result. Formal evidence then uses ten rotated control/candidate
sessions of one M64 prefill followed by 192 continuous L64--L255 decode tokens.
It must report direct token/s and the complete module table. No selected
baseline is silently changed.

## Decision state

Approved under the user's continuous decode-loop authorization on 2026-09-04.
Completed and rejected on 2026-09-04. Five rotated short sessions per cell
preserved byte-exact hashes and identical token sequences while satisfying
exact 8 MiB VTCM, zero timed intermediate DDR, zero spill/fill, one FastRPC,
no-QNN, and zero-ledger-residual requirements. The post-command control reached
20.369 token/s over the short L64--L79 decode window. Inline batch eight reached
19.605 token/s (-3.752%) and inline batch sixteen reached 19.565 token/s
(-3.946%). Gate/Up plus SwiGLU itself regressed by 10.395% and 10.264%.

The callback put expanded-slot semaphore releases and queue mutex/semaphore
publication directly on the single HMX owner's critical path. HMX-attributed
time consequently rose far more than early SwiGLU availability could hide. No
inline cell passed the bounded gate, so the approved stop condition omitted the
193-step formal run. This rejects heavy per-output callbacks, not the distinct
hypothesis of prequeued activation work with a minimal pair-ready notification.
