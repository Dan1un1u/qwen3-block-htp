# EXP-0035 — Overlap first Q-weight prefetch with input RMSNorm

## Approval and status

Approved by the user on 2026-08-28 after EXP-0034 attributed the W4F16 QKV
regression to the first Q projection plus the Q/K Norm-RoPE join tail. The
experiment starts from EXP-0034 telemetry commit
`c39dfefdb24c1bb9670a263a6605f833653800cc`. EXP-0034 changed no runtime
schedule or mathematics and is retained only to provide the per-projection
ledger.

## Motivation

At repeat ten, W4F16 Q is 4,901.7 ticks versus 3,871.6 for F16F16, while
W4F16 K and V are respectively 277.0 and 246.1 ticks faster. W4 Q expansion
and HMX wait scale approximately linearly at twice the K projection, but Q
wall and weight-DMA lifetime contain an additional roughly 1.6 to 1.8 thousand
ticks. Q is the first projection and has no preceding call from which to
receive the packed-weight cross-prefetch already available to K and V.

EXP-0035 tests one narrow hypothesis: move the exact first packed-Q weight DMA
earlier, after block input DMA has completed but before input RMSNorm begins,
so User DMA can overlap the unchanged HVX RMSNorm. The Q projection must
consume that same prefetched data without issuing a duplicate transfer.

## Fixed contract

- The Execution Unit remains one complete real Qwen3-1.7B layer-14 block at
  `M=64`, measured at repeat one and repeat ten in one FastRPC invocation.
- Controls are the EXP-0034 F16F16 batch-four and W4F16 Gate/Up batch-four,
  DMA-8, scale-cache schedules. Q/K/V order, Q/K head readiness, GQA
  Attention, streaming MLP, all weights and scales, HMX commands, arithmetic,
  output layout, and operator implementations remain unchanged.
- The candidate may move only the first Q packed-weight transfer and its wait.
  It may not transfer additional weight bytes, add a weight-DMA descriptor,
  change bundle size, pre-expand weights in DDR, or alter later Q/K/V
  cross-prefetch behavior.
- The input tensor DMA must complete before candidate Q prefetch is launched.
  The prefetch may overlap input RMSNorm but must complete before its packed
  slot is consumed. Generation/lifetime state must prevent a previous repeat
  from being reused accidentally.
- Every configuration requests and receives exactly 8,388,608 VTCM bytes.
  Existing compressed slots are reused; peak VTCM may not increase.
  Intermediate DDR, spill/fill, extra FastRPC calls, QNN, and QAIRT are hard
  failures.
- Candidate output must remain byte-identical to the W4 control and pass the
  independent Implementation Reference. F16F16 remains an immutable paired
  comparator.

## Required telemetry

Record whether Q inbound prefetch is enabled, start and completion count,
packed bytes, descriptor count, launch-to-consume lifetime, consume-side wait,
and the input-RMSNorm overlap window. Retain the EXP-0034 Q/K/V ledger. The
candidate must report exactly one moved Q transfer per block, and aggregate
weight bytes and descriptor counts must equal the W4 control.

DMA lifetime, HVX work, HMX work, and wall intervals may overlap and may not
be summed as latency. Complete-block Host wall is primary; Q wall and
consume-side wait diagnose the mechanism.

## Selection gate

Collect one audit-on correctness run and five alternating audit-off repeat-one
and repeat-ten runs for immutable F16F16 control, immutable W4F16 control, and
the Q-inbound-prefetch candidate in one stable boot. At both repeat counts a
selected candidate must:

- reduce W4F16 Q projection wall relative to W4F16 control;
- reduce complete-block W4F16 Host wall relative to W4F16 control;
- keep the W4F16 complete block strictly faster than F16F16;
- preserve byte-identical output, exact weight bytes and descriptors, HMX
  commands, 8 MiB VTCM, zero intermediate DDR, and zero spill/fill; and
- demonstrate that the moved Q transfer was consumed once without a duplicate
  or stale-repeat reuse.

No fixed percentage target is imposed. If the candidate reduces Q wall but
does not reduce complete-block Host wall, or if DMA/HVX contention moves the
same cost into input RMSNorm, the gate fails and the schedule is rejected.

## Implementation

Source commit `247ceb9a2a28a56cb0fe95dca5a23cdd54e758b0` adds one
W4F16 pipeline mode. After the blocking input-tensor DMA returns, the DSP
launches the existing asynchronous packed-weight descriptor for the first Q
bundle into the existing compressed-weight slot. Input RMSNorm then runs
unchanged on HVX. At Q entry, the existing cross-prefetch consumer waits for
and consumes that descriptor, and therefore skips the synchronous first-batch
copy that the control performs.

No new VTCM buffer, weight bundle, HMX command, tensor layout, arithmetic, or
FastRPC method was introduced. The candidate inherits the exact Gate/Up
batch-four, DMA-eight, scale-cache, Attention, and streaming-MLP schedule from
the W4 control. Dedicated telemetry records launch, consume, completion,
bytes, descriptors, lifetime, consume wait, and the input-RMSNorm overlap
window. Per-block state is initialized inside `qbh_run_one_block`, so a
descriptor cannot be reused across repeats.

## Formal outcome

The formal matrix contains 33 records in one stable device boot: one audit-on
correctness record plus five alternating audit-off repeat-one and repeat-ten
records for each of F16F16 control, W4F16 control, and the candidate. Medians
below are per complete block; lower is better.

| Repeat | Metric | F16F16 | W4F16 control | Q-prefetch candidate | Candidate vs W4 |
| --- | --- | ---: | ---: | ---: | ---: |
| 1 | Host wall, ns | 2,954,167.0 | 2,827,083.0 | 2,831,979.0 | +0.173% |
| 1 | Q projection, ticks | 3,887.0 | 4,894.0 | 4,797.0 | -1.982% |
| 10 | Host wall, ns | 2,523,750.0 | 2,411,421.9 | 2,415,776.0 | +0.181% |
| 10 | Q projection, ticks | 3,914.9 | 4,897.8 | 4,815.1 | -1.689% |

The mechanism worked exactly as intended. Each block launches, consumes, and
completes one moved descriptor containing 131,072 packed bytes. At repeat ten,
launch-to-consume lifetime is 985.6 ticks, the input-RMSNorm overlap window is
876.6 ticks, and consume-side wait is only 0.9 tick. Repeat one reports the
same relationship at 992.0, 881.0, and 1.0 ticks. The first Q bundle is thus
effectively ready when Q reaches it.

The local saving is nevertheless small. Q wall falls by 97.0 ticks at repeat
one and 82.7 ticks at repeat ten, roughly two percent. This directly falsifies
the stronger inference from EXP-0034 that the missing inbound bundle accounts
for most of Q's roughly 1.6-to-1.8-thousand-tick superlinear gap. The earlier
DMA-lifetime comparison combined all Q tiling, expansion, HMX waits, and the
outbound K prefetch inside one call boundary; it could identify Q as the slow
projection, but it could not assign that full excess to the first bundle.

Complete-block Host wall does not improve. Separate control/candidate medians
are 0.173 percent and 0.181 percent slower at repeat one and repeat ten. The
candidate remains about 4.14 percent and 4.28 percent faster than F16F16, so it
does not erase the broader W4 benefit, but it fails the strict incremental
gate. Repeat-one DSP time locally improves while Host wall does not; at repeat
ten, total DSP time rises by about 100.5 ticks per block, with small shifts in
later projection DMA, expansion, and HMX-wait intervals. The evidence supports
the conservative conclusion that the recovered Q interval is too small to
produce a reproducible end-to-end gain and can be displaced by ordinary
downstream schedule variation. It does not support attributing the failure to
one undocumented contention mechanism.

## Correctness and physical contract

The candidate is byte-identical to the W4 control with output hash
`f18b9abbe1487231`; the independent Implementation Reference reports zero
mismatches and zero maximum LSB difference. F16F16 remains unchanged with
hash `704252c89780e695`. All 118 Block Package hashes were audited.

W4 control and candidate transfer identical aggregate weight bytes and use
identical aggregate descriptor and HMX-command counts. Both request and
receive exactly 8,388,608 VTCM bytes, peak at 7,843,328 bytes, report zero
intermediate DDR and zero spill/fill, retain one FastRPC invocation per
Execution Unit and one HMX owner, and have no QNN or QAIRT dependency. The
device boot ID remained `77ccafe0-8817-4976-bdae-15af5608d4ff`.

## Decision state and follow-up boundary

EXP-0035 is `completed`, its evidence is `valid`, its `local_gate` is `fail`,
and its adoption status is `rejected`. The candidate must not replace the W4
control or become a source parent merely because Q itself improved.

This result closes the narrow cold-start hypothesis. A future Q optimization
must explain the remaining Q-only cost inside the multi-bundle
DMA-expand-HMX schedule, or change a larger cross-module critical path; moving
the same first bundle earlier is not a new hypothesis. Starting such work
requires a separately approved experiment.
