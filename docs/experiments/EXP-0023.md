# EXP-0023 — Pipelined W4F16 block acceleration

## Approval

Approved by the user on 2026-08-27: repair the W4A16 implementation and pursue
the substantial acceleration expected from its compressed W4 weight stream
relative to W16A16. Project canonical names are W4F16 and F16F16.

## Objective and hypothesis

Keep the complete real Qwen3-1.7B layer-14, `M=64` Execution Unit and Block
Package from EXP-0022. Replace only the W4F16 projection implementation that
currently decodes each W4 value, multiplies its per-output-channel scale, and
packs FP16 Crouton weights with scalar code before launching FP16 HMX.

The hypothesis is that a project-owned DMA–HVX–HMX pipeline can preserve the
approximately fourfold compressed-weight DDR reduction while hiding most W4
decode, per-channel scale, FP16 conversion, and packing work behind FP16 HMX.
The optimized W4F16 complete block should then be faster than a freshly run
F16F16 control under the same physical and measurement contract.

## Ordered implementation gates

First construct an HVX W4-to-FP16 Crouton expansion kernel. It must match the
existing scalar expansion for exhaustive W4 codes and representative real
per-channel scales, and static disassembly must prove that the hot loop uses
HVX rather than scalar per-element conversion.

Then compare the EXP-0022 scalar control with bounded-VTCM candidates that
overlap packed-W4 User DMA, HVX decode/scale/FP16 packing, and FP16 HMX. Search
buffer count, chunk size, prefetch distance, and HVX worker count without ever
materializing a full expanded projection in DDR. Gate/Up and Down must be
included because they dominate the defective implementation; Q/K/V/O must also
use the selected physical plan before whole-block timing.

Finally run the complete F16F16 and selected W4F16 blocks with one full warm-up
block and five repeat-one plus five repeat-ten measured invocations. Equivalent
Host-wall latency is primary. A valid local speed result requires W4F16 to be
strictly faster than the freshly measured F16F16 control in both repeat-one and
repeat-ten medians. A repeat-ten improvement of at least 15% is the experiment
target, not an automatic adoption rule. Report projection-stage ticks, weight
DDR bytes, HVX/HMX overlap, waits, VTCM peak, and all physical gates.

No result becomes a Selected Baseline without explicit user approval. If the
strict speed gate fails after the declared schedule search, record the result
and stop for discussion instead of weakening the numerical, VTCM, or DDR
contract.

## Implemented pipeline

The retained source head is
`896446df77cca17ad8f6c1940f09461a0f99d4af`. The final W4F16 path keeps all
projection inputs, expanded weights, and outputs in one exact 8 MiB VTCM
session. It reads signed per-output-channel W4 weights in batches of four
32-channel output tiles, directly maps each nibble to an FP16 bit pattern with
HVX `vlut16`, and uses two HVX worker threads plus the FastRPC thread to expand
the next tile group while HMX executes the current group. Per-channel scales
remain cached in VTCM and are applied by the FP16 HMX output-scale path rather
than by a separate elementwise multiply.

Two adjacent 32-channel output tiles are expanded and submitted together. The
two-tile physical plan halves W4 projection HMX worker commands from 640 to
320 per block, reduces steady-state weight DMA descriptors from 640 to 160
plus seven one-time scale-cache descriptors, and lets output unpack use the
two-tile HVX path. Fourfold compressed weights and two expanded-weight groups
are double buffered, so packed-W4 DMA, HVX expansion, and FP16 HMX overlap
without writing an expanded tile to DDR.

The schedule search also produced two rejected candidates that constrain
future work. Equal static 22/21/21 K-tile partitions were slower than dynamic
region claiming because the participating HVX contexts were not effectively
equal-speed; the slowest static partition became the barrier. A three-output-
tile HMX batch fit under 8 MiB at 8,334,592 bytes, but immediately generated
non-finite values and failed the numerical gate. The retained two-tile plan is
therefore the fastest candidate that satisfies the complete physical and
mathematical contract.

## Interpretation

The original scalar W4F16 path from EXP-0022 required about 3.004 seconds per
block. The retained DMA-HVX-HMX pipeline reduces that to 194.131 ms, a 15.47x
repair, and makes compressed W4 weights genuinely faster than F16 weights in
the projection subsystem. This validates the intended physical mechanism:
weight compression saves off-chip traffic, while direct SIMD expansion and
double buffering hide much of the reconstruction work behind HMX.

The small complete-block gain is not evidence that the repaired W4 pipeline
is ineffective. In the repeat-ten F16F16 control, all four projection stages
account for only about 3.59% of total DSP ticks. The remaining approximately
96.41% is shared scalar/reference implementation work in RMSNorm, Q/K norm,
RoPE, causal Softmax, activation, and related movement. Even deleting all
projection time could not reach a 15% whole-block improvement under that
current common-stage implementation. The next performance experiment must
optimize those common stages identically for F16F16 and W4F16 before the
projection-level benefit can become a substantial end-to-end block speedup.

Execution is complete, evidence is valid, and the strict local speed gate
passes. On 2026-08-28 the user temporarily accepted this result as the
Provisional Source Parent for the FP16 common-operator experiment. This accepts
the experiment result without promoting a Selected Baseline; that field remains
unset.
