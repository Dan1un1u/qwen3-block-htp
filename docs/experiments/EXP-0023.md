# EXP-0023 — Pipelined W4F16 block acceleration

## Approval

Approved by the user on 2026-08-27: repair the W4A16 implementation and pursue
the substantial acceleration expected from its compressed W4 weight stream
relative to W16A16. Project canonical names are W4F16 and F16F16.

## Objective and hypothesis

Keep the complete real Qwen3-1.7B layer-14, `M=64` Execution Unit and Block
Package from EXP-0022. Replace only the W4F16 projection implementation that
currently decodes each W4 value, multiplies its per-output-channel scale, and
packs FP16 Crouton weights with scalar code before launching FP16 HMX.

The hypothesis is that a project-owned DMA–HVX–HMX pipeline can preserve the
approximately fourfold compressed-weight DDR reduction while hiding most W4
decode, per-channel scale, FP16 conversion, and packing work behind FP16 HMX.
The optimized W4F16 complete block should then be faster than a freshly run
F16F16 control under the same physical and measurement contract.

## Fixed contracts

- Source begins at EXP-0022 head
  `25157d78f13e4be8215530639b166e772eaadb2c` on the independent branch
  `codex/exp-0023-w4f16-pipeline`.
- The real layer-14 input, FP16 teacher, signed-symmetric per-output-channel W4
  values in `[-7, 7]`, scales, FP16 activations, output reference, and all
  non-projection block arithmetic remain unchanged.
- Legal DDR remains limited to block input, immutable compressed weights and
  metadata, and final output. Expanded FP16 weight tiles are temporary VTCM
  state. Intermediate DDR read/write, spill/fill, graph split, CPU fallback,
  QNN, and QAIRT remain hard failures.
- Each formal variant receives one exact 8 MiB Fixed Full-VTCM Session. HMX
  FP16 Crouton activation, weight, and output addresses remain 2 KiB aligned;
  bias/scale storage remains 256-byte aligned.
- FP16 HMX arithmetic is unchanged. This experiment optimizes physical data
  preparation and scheduling; it does not change the W4 quantization recipe or
  substitute integer HMX.
- Device output must retain the EXP-0022 W4F16 implementation-reference gate:
  finite output, cosine at least 0.99999, and maximum absolute error no greater
  than 0.0625. Teacher error is reported only as a diagnostic.

## Ordered implementation gates

First construct an HVX W4-to-FP16 Crouton expansion kernel. It must match the
existing scalar expansion for exhaustive W4 codes and representative real
per-channel scales, and static disassembly must prove that the hot loop uses
HVX rather than scalar per-element conversion.

Then compare the EXP-0022 scalar control with bounded-VTCM candidates that
overlap packed-W4 User DMA, HVX decode/scale/FP16 packing, and FP16 HMX. Search
buffer count, chunk size, prefetch distance, and HVX worker count without ever
materializing a full expanded projection in DDR. Gate/Up and Down must be
included because they dominate the defective implementation; Q/K/V/O must also
use the selected physical plan before whole-block timing.

Finally run the complete F16F16 and selected W4F16 blocks with one full warm-up
block and five repeat-one plus five repeat-ten measured invocations. Equivalent
Host-wall latency is primary. A valid local speed result requires W4F16 to be
strictly faster than the freshly measured F16F16 control in both repeat-one and
repeat-ten medians. A repeat-ten improvement of at least 15% is the experiment
target, not an automatic adoption rule. Report projection-stage ticks, weight
DDR bytes, HVX/HMX overlap, waits, VTCM peak, and all physical gates.

No result becomes a Selected Baseline without explicit user approval. If the
strict speed gate fails after the declared schedule search, record the result
and stop for discussion instead of weakening the numerical, VTCM, or DDR
contract.
