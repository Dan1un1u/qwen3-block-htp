## Motivation

At repeat ten, the EXP-0029 W4F16 candidate takes 4.494 ms per complete block.
Its sequential Gate/Up, SiLU-by-Up, and Down intervals take approximately
0.994 ms, 1.682 ms, and 0.342 ms respectively, so the gated MLP occupies about
3.017 ms or 67% of the Host boundary. The current SiLU-by-Up kernel uses HVX
SIMD but executes one complete 393,216-element pass on one calling context.
Gate, Up, the complete activation pass, and Down remain separated by global
barriers.

The formal mllm W4A16 trace is not a performance comparator for this project,
but it is valid physical-scheduling evidence. Its Gate and Up spans overlap,
Down begins before either producer span ends, no standalone physical Sigmoid
appears, and `q::Swish_16` plus `q::mul_op` work is attributed inside the Down
projection with up to six-way parallelism. This motivates reproducing the
causal tile schedule in the project-owned runtime without QNN.

## Fixed contract

- The Execution Unit remains one complete real Qwen3-1.7B layer-14 block at
  `M=64` in one FastRPC invocation. Formal timing retains repeat one and repeat
  ten.
- F16F16 keeps EXP-0027's double-buffered batch-two projection schedule.
  W4F16 keeps EXP-0028's adaptive 32/96-region pipeline and cross-projection
  prefetch. Attention keeps EXP-0029's combined direct-HVX Crouton packing.
- RMSNorm, RoPE, Attention, projection weights, W4 values and scales, HMX
  arithmetic, SiLU mathematics, residuals, and output arithmetic remain
  unchanged. W4U8 is outside this experiment.
- Every mode requests and receives exactly 8,388,608 VTCM bytes. Gate, Up,
  activated intermediate, and Down partial/output state remain in VTCM or
  accelerator state. Intermediate DDR, spill/fill, extra FastRPC calls, QNN,
  and QAIRT are hard failures.
- Equivalent-scope Host wall is primary. The Block Timing Ledger remains
  exclusive and closed. HMX, HVX, DMA, worker waits, and readiness counters are
  diagnostic and may not be summed as latency.
- Candidate output must remain byte-identical to its paired EXP-0029 control,
  in addition to passing the existing Implementation Reference and non-finite
  checks.

## Ordered milestones

### A — Multi-worker SiLU-by-Up

Partition the existing FP16 HVX vector loop into bounded aligned ranges served
by persistent HVX workers. Preserve the exact per-element instruction sequence
and output bytes. Compare one, two, three, and available-worker plans with the
same search budget for F16F16 and W4F16. This is a single-variable diagnostic:
it may be retained only if it reduces the activation interval without
regressing complete-block Host wall.

A correct but slower result does not by itself close the experiment, because
the main hypothesis is removal of the full-tensor producer/consumer barriers.
A numerical mismatch, intermediate DDR, resource-grant failure, or unstable
worker handoff stops the experiment before streaming work.

### B — Tile readiness and direct Down carrier

Define one bounded intermediate-channel slab whose Gate and Up output tiles
can be paired. Publish matching tiles with generation-tagged release/acquire
semantics. HVX applies the unchanged SiLU-by-Up computation and writes directly
to the exact Crouton activation carrier required by Down HMX, rather than
waiting for or rescanning a complete flat `middle` tensor.

### C — Down accumulation pipeline

Allow Down weight prefetch/expansion and Down HMX accumulation to begin as soon
as the required activated K slab is ready. Preserve the original K traversal
and accumulation order so the output hash remains stable. HMX ownership remains
serialized, while DMA and non-conflicting HVX work may overlap it. Buffer reuse
must be proven by explicit peak-live VTCM accounting.

### D — Complete-block gate

Evaluate the final streaming candidate against the immutable EXP-0029 control
for both F16F16 and W4F16. Collect audit-on correctness and alternating
audit-off repeat-one/repeat-ten timing in one stable boot. The local gate
requires lower complete-MLP exclusive ticks and no Host-wall regression for
both variants at both repeat counts. W4F16 must remain strictly faster than
F16F16. No fixed percentage target is imposed.

## Implementation result

Milestone A retained the exact SiLU instruction sequence and divided its 6,144
FP16 channels among the calling context and three persistent HVX workers. This
reduced the standalone activation interval from about 32.73 thousand ticks per
block to 8.24 thousand ticks for both projection variants, and reduced complete
block Host wall for both repeat one and repeat ten.

Milestone B uses generation-tagged 64-channel readiness groups. As matching
Gate and Up groups become available, HVX computes the unchanged SiLU-by-Up
result and writes that group directly into the Crouton activation carrier used
by Down HMX. The old full-tensor Down activation pack is skipped. F16F16 uses
three streaming workers. W4F16 alternates matching Gate and Up groups while its
existing workers continue W4 expansion; one spare worker consumes groups during
that overlap, then the released expansion workers and the main context drain a
bounded tail. Gate, Up, activated intermediate, and the Down carrier remain in
the fixed 8 MiB VTCM allocation.

Milestone C's stronger form, beginning Down HMX accumulation before all K slabs
are complete, was not implemented. The available single-context HMX path cannot
retain a Down accumulator while it is reused by later Gate and Up commands.
The reference chunked `C += A*B` form stores and reloads FP16 partial outputs
between K slabs, which changes the rounding sequence and violates the required
byte-identical output hash. Adding a second HMX ownership domain would change
the fixed resource contract. The retained result therefore streams through the
exact Down carrier and overlaps HVX preparation, but starts Down HMX after the
Gate/Up producer commands finish.

## Formal evidence and gate

The formal matrix contains 66 records: audit-on correctness plus five
alternating audit-off repeat-one and repeat-ten runs for F16F16 and W4F16 in
control, multi-worker-SiLU, and streaming modes. The device boot ID remained
stable. Both streaming variants use exactly 8,388,608 VTCM bytes, report zero
intermediate DDR reads and writes, zero spill/fill, 352 HMX commands per block,
96 published/consumed MLP groups, and one skipped Down full-carrier pack per
block. F16F16 retains output hash `704252c89780e695`; W4F16 retains
`f18b9abbe1487231`. Their Implementation Reference cosine values are above
0.99999999 and maximum absolute error is 0.0625.

| Formal median | F16 control | F16 streaming | W4 control | W4 streaming |
| --- | ---: | ---: | ---: | ---: |
| repeat1 Host wall | 5.259 ms | 3.542 ms | 4.929 ms | 3.419 ms |
| repeat10 Host wall/block | 4.836 ms | 3.161 ms | 4.507 ms | 3.019 ms |
| repeat10 complete MLP | 64.504 ktick | 32.290 ktick | 58.283 ktick | 29.581 ktick |

At repeat one, streaming changes complete-block Host wall by -32.66% for
F16F16 and -30.63% for W4F16. At repeat ten, the changes are -34.64% and
-33.01%. The final W4F16 streaming result is 4.48% faster than the F16F16
streaming result at repeat ten. Every local gate passes, including the strict
requirement that W4F16 remain faster than F16F16. This is a successful local
candidate, but only the user may approve its adoption.
