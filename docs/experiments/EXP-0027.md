# EXP-0027 — Fair F16F16 weight-flow pipeline

## Approval and status

Approved by the user on 2026-08-28 after EXP-0026 removed the scalar residual
bottleneck. This experiment determines whether the current F16F16 projection
path is genuinely weight-flow bound and removes schedule defects from the
W16A16 control before interpreting the W4F16 speedup. It does not accept
EXP-0026, promote a Selected Baseline, or change EXP-0023's role as the
Provisional Source Parent.

## Existing evidence and hypothesis

EXP-0026's selected complete-block candidate reads 100,663,296 FP16 weight
bytes per F16F16 block. Its four projection groups occupy 67,868.0 exclusive
DSP ticks. The overlapping explanatory counters report 37,580.3 weight-DMA
ticks, 24,627.1 HMX wait-envelope ticks, and only 6,312.5 raw HMX compute
ticks. F16F16 transfers one N tile synchronously and waits for one HMX command
before starting the next tile, while W4F16 already batches two N tiles and
prefetches compressed weights.

The hypothesis is twofold. First, F16F16 projection is empirically dominated by
weight movement and command publication rather than HMX arithmetic. Second,
the current serial F16 physical plan leaves avoidable DMA--HMX overlap and
command batching overhead, so it is not yet a fair optimized control for the
W4F16 pipeline.

## Ordered milestones

### A — Memory-bound attribution

Reproduce the serial F16F16 control and report exclusive projection ticks,
weight bytes, weight-DMA span, HMX wait envelope, raw HMX work, pack/unpack,
descriptor count, command count, and effective projection weight bandwidth.
Treat engine counters as overlapping explanatory data, not additive block
latency. The conclusion must distinguish projection-level weight-flow
dominance from complete-block Amdahl dilution.

### B — Asynchronous single-tile control

Use the existing pair of aligned FP16 weight slots to overlap the next User-DMA
transfer with current HMX consumption while retaining one N tile per command.
This isolates overlap from HMX batching. It must preserve exact output hashes,
weight bytes, numerical gates, and zero-intermediate-DDR behavior.

### C — Double-buffered batch-two F16F16

Evaluate two contiguous N tiles per weight buffer and HMX command, with two
buffers alternating between User DMA and HMX. The plan may use additional VTCM
inside the common 8 MiB grant and must report its peak. It must not overwrite a
buffer before both its DMA producer and HMX consumer finish.

The selected F16F16 plan is the fastest valid repeat-ten Host-wall candidate
that does not regress repeat-one Host wall. If neither candidate improves the
serial control, retain the serial control and record the failed schedule
hypothesis.

### D — Fair W4F16 comparison and stop point

Compare the unchanged current W4F16 pipeline against the selected F16F16 plan
using one artifact set, boot, instrumentation contract, and alternating run
order. Report both projection-only and complete-block changes. If W4F16 no
longer wins, stop and discuss W4 expansion/DMA/HMX scheduling before optimizing
shared operators. If W4F16 wins, use the measured Amdahl floor to choose between
W4 pipeline work and the shared QK/AV packing path in a separate experiment.

## Implementation

Source commits `9ef94a987e9e0148649069893af33eda64f3af6f` and
`cc88df0a5e8f927daedeb43803e3d2073045736d` add three explicit F16F16
projection schedules and a formal alternating matrix. The asynchronous
single-tile schedule overlaps the next FP16 weight DMA with current HMX work.
The double-buffered batch-two schedule stores two contiguous N tiles in each of
two alternating VTCM buffers, reducing both weight descriptors from 640 to 320
and HMX commands from 672 to 352 per block. Its peak plan is 7,072,512 bytes,
inside the unchanged exact 8 MiB VTCM grant.

## Formal outcome

Formal run
`D:\llm_exp\results\qwen3-block-htp\exp0027\20260828T074150Z_cc88df0a5e8f`
contains 44 records: one audit-on correctness record plus five alternating
audit-off repeat-one and repeat-ten records for each of four schedules. The
Block Package hashes, boot ID, binaries, timing ledgers, exact 8 MiB VTCM
grant, zero-intermediate-DDR contract, and F16F16 output hashes all pass.

The selected F16F16 schedule is double-buffered batch-two. At repeat ten, it
reduces complete-block Host wall from 13.6599427 ms to 12.3994115 ms
(-9.2279%) and projection ticks from 67,446.5 to 43,521.5 (-35.4726%). The
serial control's weight-DMA span is 5.9689 times its raw HMX work, and the
selected schedule sustains 44.4087 GB/s effective projection weight bandwidth.
This confirms that F16F16 projection is weight-flow and command-flow dominated,
while also proving that the old serial control was materially under-optimized.

The unchanged W4F16 control reads only 25,174,016 weight bytes per block versus
100,663,296 for F16F16, but records 35,275.2 W4-expansion ticks and a 38,921.8
tick HMX hand-off/wait envelope. It therefore takes 46,675.3 projection ticks
and 12.5856146 ms Host wall: 7.2465% slower in projections and 1.5017% slower
for the complete block than the fair F16F16 schedule. The apparent W4F16 win
against the former serial control was not a valid optimized comparison.

The experiment's F16 schedule gate passes, but its fair W4 performance result
is negative. Per the approved stop condition, no shared Attention, SiLU, or
other common-operator optimization follows automatically. The next proposed
experiment must first address W4 expansion, producer/consumer hand-off, and
DMA--HVX--HMX overlap, then compare against this selected F16F16 control.
