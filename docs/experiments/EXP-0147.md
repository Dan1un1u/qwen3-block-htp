# EXP-0147 — Selected-baseline multi-M and KV-cache generalization scan

## Decision and purpose

The user approved this experiment on 2026-09-01 as the transition from fixed
`M=64` single-block schedule tuning to shape generalization. The immutable
reference implementations are the selected F16F16 public baseline EXP-0109,
the selected fastest W4F16 baseline EXP-0140, and the selected fastest W4U8
baseline EXP-0144. EXP-0147 is a characterization and substrate experiment;
it does not promote a new recipe-fastest baseline and must not silently retune
the selected `M=64` kernels.

The experiment asks two separate questions. The prefill track measures
`M={16,32,64,128}` with causal self-attention length equal to `M`. The decode
track measures `M=1` with declared persistent KV-cache lengths
`L={64,256,1024,4096}` and appends the current token's K/V exactly once. These
tracks must remain distinct because projection row utilization and Attention
working-set growth have different physical causes.

## Fixed implementation boundary

The Execution Unit remains one real Qwen3 layer-14 middle block in one
project-owned FastRPC invocation with no QNN. The current selected numerical
recipes, weights, qparams, operator mathematics, physical HMX instruction
family, and one-HMX-owner rule are fixed. Shape support may add tail handling,
row tiling, cache addressing, and bounded Attention tiling, but it may not tune
an existing `M=64` schedule, change a quantization recipe, introduce a hidden
DDR workspace, or combine the scan with a new kernel optimization.

The KV cache is a declared persistent Native Boundary object and therefore may
reside in DDR. QK scores, Softmax probabilities, projection intermediates,
residuals, and all other temporary block values remain forbidden from DDR.
KV-cache traffic must be reported separately from intermediate traffic so that
the zero-intermediate-DDR contract cannot be satisfied by relabeling scratch as
cache.

The implementation must preserve the selected source identities explicitly:

* F16F16: EXP-0109 commit `42e2a33012929ccbb05e8c2741124b6fd539552c`;
* W4F16: EXP-0140 commit `e75563457293de9430f8c9d20a04ced6147e4737`;
* W4U8: EXP-0144 commit `919aaa74870661d78b92e64976e695a4fa87f955`.

If they cannot be represented in one source tree without changing their
selected `M=64` paths, they must be built from their immutable tags and driven
through one common external scan harness rather than merged approximately.

## Stages and gates

Stage A is a static/source capability audit. It must identify every compile-time
`M=64` assumption, HMX tail constraint, tensor extent, VTCM lifetime, causal
mask assumption, and missing KV-cache boundary. It must also prove a feasible
8 MiB peak plan for each proposed cell before hardware execution. A cell may be
reported unsupported when the current physical instruction contract cannot
represent it safely; unsupported is evidence, not permission to pad silently
without attribution.

Stage B establishes correctness. The existing `M=64` cells must reproduce the
selected baseline outputs and profiling contract. Every new prefill cell must
match an independent recipe-specific block reference under its declared tail
and padding rules. Every decode cell must match the same reference for final
block output and the appended K/V bytes. W4U8 integer boundaries require zero
LSB mismatch; FP16 paths retain their existing experiment tolerance and audit
rules. Quantization fidelity relative to a teacher is reported separately and
is not a stop gate for this performance-generalization experiment.

Stage C proves the physical contract: exactly 8 MiB VTCM requested and
acquired, zero intermediate DDR and spill/fill, one FastRPC Execution Unit, one
HMX owner, no CPU/QNN fallback, and explicit KV-cache DDR read/write bytes.
Scores and probabilities may be tiled in VTCM but must never become DDR
tensors.

Stage D performs the scan with repeat one and repeat ten and reports complete
Block Timing Ledgers and engine counters. Formal comparison is descriptive:
latency, useful-token throughput, padding/utilization, DMA/HVX/HMX shares, and
KV-cache traffic are required for all supported cells. There is no speed gate
and no baseline promotion. The experiment passes only when all supported cells
close correctness, physical, and profiling evidence and every unsupported cell
has a specific architectural reason.

The work stops for discussion if the `M=64` selected paths cannot be preserved,
if KV-cache state requires an intermediate DDR spill, or if any requested shape
requires changing recipe mathematics rather than adding shape mechanics.
