# EXP-0047 — Same-commit W4F16/W4U8 critical-path attribution

## Approval and parent

Approved by the user on 2026-08-29 after EXP-0046 established the latest
W4U8 candidate and the user requested that the next optimization decision be
based on a complete comparison with W4F16. The implementation parent is
EXP-0046 source head `40da9f06f6a5d8335d0b9a0c45f7efa61525c50f`.
The source branch is `codex/exp-0047-w4f16-w4u8-profile`.

## Question and comparison semantics

This is a characterization experiment, not a new optimization and not a
baseline-promotion experiment. It asks why the current fastest W4U8 path is
still slower than the selected W4F16 baseline, and which complete-block stages
and overlapping DMA, HVX, and HMX intervals dominate that gap.

The primary comparison is current-best versus current-best on one source
commit and one device boot. W4F16 reproduces the selected
`W4F16-EXP0038-NORMS` runtime plan; W4U8 reproduces
`W4U8-EXP0046-NATIVE-MLP-IO`. Because the two variants intentionally use
different activation arithmetic, Attention implementation, layout boundaries,
and tuned schedules, this result must not be described as an identical-plan
single-variable comparison. The shared W4 values and scales must nevertheless
be proven byte-identical before timing conclusions are admitted.

## Fixed contract and completion gates

- The Execution Unit is the real Qwen3 layer-14 complete block at M=64.
- Both variants are built from the same source commit, packaged together where
  supported, deployed together, and measured on one stable device boot.
- W4F16 uses the selected EXP-0038 `norms` plan, including its accepted
  projection, Attention, MLP, and Crouton-boundary settings. W4U8 uses the
  complete EXP-0046 plan, including integer Attention, QKVO batch four, and
  native MLP input/output boundaries.
- Each variant must independently pass its declared implementation reference,
  output-hash stability, and numerical diagnostics. Cross-variant byte equality
  is neither expected nor required.
- One FastRPC invocation per block execution unit, one HMX owner, exactly
  8 MiB VTCM, zero intermediate DDR, zero spill/fill, and no QNN path are
  mandatory for both variants.
- Seven interleaved paired rounds are required at repeat one and repeat ten on
  one stable boot. Host wall per block is the primary latency measure.
- There is no speed gate and no automatic adoption decision. Completion means
  that correctness and physical gates pass and the PC-027 report fully closes
  the additive block ledger plus overlapping projection, Attention, MLP, DMA,
  HVX, HMX, readiness, slot-pressure, and lifetime diagnostics.
- The report must separate mutually exclusive ledger rows from overlapping
  engine-work counters, quantify every W4U8-minus-W4F16 gap, and identify which
  hypotheses are supported, rejected, or still unobservable.

## Formal result

The characterization completed on source commit
`f8897405621b769f5e32a2690cea7399b215d59e`. Seven interleaved paired rounds
on stable boot `77ccafe0-8817-4976-bdae-15af5608d4ff` reproduce the selected
W4F16 plan at 2.6405 ms/block for repeat one and 2.2195 ms/block for repeat
ten. The current W4U8 plan measures 6.1353 and 5.7515 ms/block, respectively,
or 132.35% and 159.14% slower. This experiment has no speed gate; the
completion gate passes because both paths satisfy their own numerical and
physical contracts and the complete PC-027 evidence closes.

The additive repeat-ten gap is 67.8k qtimer ticks/block. Gate/Up contributes
26.4k ticks (38.9% of the net gap), QKV contributes 23.0k (33.9%), O
projection 6.6k (9.7%), Attention 5.3k (7.9%), and Down 3.1k (4.5%). The
shared W4 bundle digest is
`fd016578c132a7917faf79fc939faf88eb2afb4c922313e40794521e32215b22`;
W4U8 therefore reads approximately the same weight bytes rather than gaining
additional weight-bandwidth reduction.

The decisive physical difference is submission granularity. W4F16 executes
208 HMX commands/block and carries 475.1 FP16 tile pairs per command. W4U8
executes 1040 commands/block and carries 47.5 U8xS8 tile pairs per command.
Although the carrier-specific tile-pair total is halved, command count is
five times higher and payload per command is one tenth. W4U8 also spends about
21.1k ticks/block in projection packing, versus 0.1k for W4F16, and reports
about 32.1k overlapping expanded-slot-wait ticks in the MLP. W4F16 reports
more DMA work but hides it behind expansion and HMX; W4U8's finer submissions,
carrier construction, and producer-consumer cadence remain on the critical
path.

Both variants use the same package and byte-identical W4 values/scales, one
FastRPC execution unit, one HMX owner, exactly 8 MiB requested/acquired VTCM,
zero intermediate DDR, zero spill/fill, and no QNN or CPU fallback. W4F16
retains output hash `f18b9abbe1487231`; W4U8 retains
`69f22eeb035e5ec5`, and its independent integer QK, log2-Softmax, and AV
references have zero mismatches. These are local implementation-correctness
results and do not establish full-model W4U8 accuracy.
