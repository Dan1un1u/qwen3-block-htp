# EXP-0158 — HMX-native persistent KV cache for both A16 recipes

## Decision and purpose

EXP-0157 demonstrated that a persistent HMX-native cache plus prefill carrier
reuse removes both W4U8 decode prefix reconstruction and duplicate prefill
carrier construction.  On 2026-09-02 the user directed that the same physical
principle be applied to F16F16 and W4F16 so the three recipes are compared at a
comparable cache-optimization level.

## Fixed boundary

The immutable source parent is EXP-0157 commit
`0a3557d075dc4c2b3e4a0d9e05910acb3cf4bf6b`.  This experiment may change only
the F16F16 and W4F16 persistent K/V cache ABI, the lifetime and transfer of
their prefill QK/AV carriers, their current-token decode cache update and the
corresponding QK/AV cache consumers.  Projection kernels and schedules,
RMSNorm, RoPE, Softmax and Attention arithmetic, MLP, model values, W4 values
and the accepted W4U8 path remain unchanged.

For each recipe the direct control is its same-binary row-major persistent
cache path.  The candidate stores a versioned FP16 HMX-consumable K/V carrier,
reuses the already-constructed prefill carriers while initializing only padded
tail state, and updates only the current token lane during decode.  It may not
hide a logical cache replica or workspace in Host memory or intermediate DDR.

The execution unit is real Qwen3 layers 0 through 27, one M64 prefill followed
by continuous decode positions 64 through 71, with one FastRPC invocation per
full-stack step.

## Gates

Both candidates must retain the user-approved scheme-1 FP16 conditional and
composed-output correctness contract, valid cache structure, byte-stable old
prefixes and no non-finite values.  Direct-control comparison remains visible
as a diagnostic.  Every candidate layer must report zero duplicate full
prefill construction and every decode step must report zero complete-prefix
pack, with only the current token updated.

The physical contract remains exact 8 MiB VTCM, zero intermediate DDR, zero
spill/fill, one FastRPC call per full-stack step, one HMX owner and no QNN.
For both F16F16 and W4F16, candidate M64 prefill and continuous-decode Host wall
must each be strictly lower than its own same-binary row-major control.  The
fairness gate requires the same cache-native lifetime and incremental-update
principle for both recipes; only the carrier encoding may differ where the HMX
operand format requires it.

Implementation proceeds through a single-layer smoke for each recipe before
the 28-layer run.  Any correctness, structural, physical or two-recipe speed
failure, or a device reboot, stops the experiment for discussion.  Passing
does not promote either A16 baseline automatically.

## Completed implementation

The source implementation is fixed at commit
`264c911a65a341f00450855cf89b2d89bbd5f108` on
`codex/exp-0158-a16-hmx-native-kv-cache-parity`. Both A16 recipes use the
same versioned physical principle: persistent storage contains the exact M64
K and V carriers already consumed by prefill HMX, followed by an eight-token
contiguous row journal. Each decode step appends only its current K/V row.
The dynamic Attention path reads the compact carrier and journal into VTCM,
uses HVX packing/copy operations to patch the bounded tail tile, and submits
the unchanged QK and AV HMX operations. There is no logical cache replica.

An early scalar tail-patch prototype was rejected inside the experiment
because it was numerically correct but made decode slower. The final HVX tile
patch and compact M64 base remove that scalar cost and keep average decode
cache bytes equal to the row-major control.

## Formal result

Formal evidence is retained at
`D:/llm_exp/results/qwen3-block-htp/exp0158/20260902T071708Z_264c911a65a3_formal`.
It contains ten rotated complete four-variant runs, each consisting of one
real 28-layer M64 prefill followed by continuous decode positions 64-71.

| Recipe | Layout | Prefill M64 | Prefill tok/s | Decode/token | Decode tok/s |
|---|---|---:|---:|---:|---:|
| F16F16 | row-major control | 93,620.469 us | 683.611 | 95,533.581 us | 10.468 |
| F16F16 | HMX-native candidate | 67,212.812 us | 952.199 | 95,282.468 us | 10.495 |
| W4F16 | row-major control | 118,201.562 us | 541.448 | 84,123.952 us | 11.887 |
| W4F16 | HMX-native candidate | 54,443.282 us | 1,175.535 | 83,679.518 us | 11.950 |

F16F16 improves prefill speed by 39.290% and decode speed by 0.264%.
W4F16 improves prefill speed by 117.110% and decode speed by 0.531%.
All four strict speed comparisons therefore pass. The candidate paths reuse
7,340,032 bytes of populated prefill carriers. Candidate decode performs zero
complete-prefix packs and writes exactly 114,688 cache bytes per full
28-layer token step.

All nine outputs for both recipes pass the user-approved scheme-1 FP16
composition gate. Cache structure and old prefixes are valid, with no
non-finite values. Every formal record obtains exactly 8 MiB VTCM, reports
zero intermediate DDR reads and writes, zero spill/fill, one FastRPC call per
full-stack step, one HMX owner, no QNN and zero ledger-unattributed ticks. The
device boot ID is unchanged.

## Decision state

Execution, evidence, local, structural, physical, fairness and speed gates
are complete and pass. On 2026-09-02 the user explicitly accepted EXP-0158
and promoted both candidates as the selected full-stack F16F16 and W4F16
cache-native baselines. This promotion is scoped to real 28-layer M64 prefill
and continuous decode positions 64-71; it does not replace the frozen Public
Common Baseline or either recipe's single-block fastest baseline. EXP-0158 is
the first selected three-recipe full-stack comparison in which F16F16, W4F16
and W4U8 all use cache-native persistent Attention state.
