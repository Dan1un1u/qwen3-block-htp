# EXP-0158 — HMX-native persistent KV cache for both A16 recipes

## Decision and purpose

EXP-0157 demonstrated that a persistent HMX-native cache plus prefill carrier
reuse removes both W4U8 decode prefix reconstruction and duplicate prefill
carrier construction.  On 2026-09-02 the user directed that the same physical
principle be applied to F16F16 and W4F16 so the three recipes are compared at a
comparable cache-optimization level.

## Fixed boundary

The immutable source parent is EXP-0157 commit
`0a3557d075dc4c2b3e4a0d9e05910acb3cf4bf6b`.  This experiment may change only
the F16F16 and W4F16 persistent K/V cache ABI, the lifetime and transfer of
their prefill QK/AV carriers, their current-token decode cache update and the
corresponding QK/AV cache consumers.  Projection kernels and schedules,
RMSNorm, RoPE, Softmax and Attention arithmetic, MLP, model values, W4 values
and the accepted W4U8 path remain unchanged.

For each recipe the direct control is its same-binary row-major persistent
cache path.  The candidate stores a versioned FP16 HMX-consumable K/V carrier,
reuses the already-constructed prefill carriers while initializing only padded
tail state, and updates only the current token lane during decode.  It may not
hide a logical cache replica or workspace in Host memory or intermediate DDR.

The execution unit is real Qwen3 layers 0 through 27, one M64 prefill followed
by continuous decode positions 64 through 71, with one FastRPC invocation per
full-stack step.

## Gates

Both candidates must retain the user-approved scheme-1 FP16 conditional and
composed-output correctness contract, valid cache structure, byte-stable old
prefixes and no non-finite values.  Direct-control comparison remains visible
as a diagnostic.  Every candidate layer must report zero duplicate full
prefill construction and every decode step must report zero complete-prefix
pack, with only the current token updated.

The physical contract remains exact 8 MiB VTCM, zero intermediate DDR, zero
spill/fill, one FastRPC call per full-stack step, one HMX owner and no QNN.
For both F16F16 and W4F16, candidate M64 prefill and continuous-decode Host wall
must each be strictly lower than its own same-binary row-major control.  The
fairness gate requires the same cache-native lifetime and incremental-update
principle for both recipes; only the carrier encoding may differ where the HMX
operand format requires it.

Implementation proceeds through a single-layer smoke for each recipe before
the 28-layer run.  Any correctness, structural, physical or two-recipe speed
failure, or a device reboot, stops the experiment for discussion.  Passing
does not promote either A16 baseline automatically.
