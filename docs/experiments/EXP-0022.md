## Numerical variants

F16F16 stores real layer weights as FP16 and uses FP16 activations with FP16
HMX. W4F16 quantizes each projection weight once to signed symmetric W4 in
`[-7, 7]` with one scale per output channel, expands that carrier for FP16 HMX,
and retains FP16 activations. W4U8 uses byte-identical W4 values and scales,
expands to S8, and uses asymmetric U8 activations with explicit zero-point
correction on integer HMX.

Fresh U8 encodings are generated from the captured real block execution at
named activation boundaries. Device implementations are validated against
independent references of their own declared arithmetic. F16F16 teacher error,
W4F16 error, and W4U8 error relative to the original BF16 layer are reported as
diagnostics; there is no whole-model quality gate.

## Physical boundary and gates

The legal DDR tensors are the block input, immutable Block Package weights and
metadata streamed by User DMA, and final block output. All RMSNorm outputs,
Q/K/V, normalized and rotated heads, attention scores/probabilities, attention
output, residual states, Gate/Up tiles, activated MLP middle, and Down input are
intermediate tensors and may exist only in HMX state, HVX registers, or the
declared VTCM arena. Intermediate DDR reads/writes, intermediate DMA to DDR,
spill/fill, CPU fallback, QNN/QAIRT, graph split, and multiple run calls for one
logical block are hard failures.

Milestones are ordered. First pass the exact full-VTCM capability gate. Then
generate and audit the real Block Package and Host references. Bring up F16F16,
then W4F16, then W4U8 with one-block correctness before performance runs.
Failure of one numerical path does not authorize weakening the resource or DDR
contract. Formal timing uses a complete warm-up block followed by one complete
measured invocation; repeat-one and repeat-ten Host-wall medians are primary.

All three variants receive the same schedule-search budget and selection rule.
There is no hard speed threshold in this first full-block comparison. The
result must report equivalent-scope latency, requested/granted/peak VTCM, DDR
weight bytes, HMX/HVX/DMA overlap, stage timings, and numerical diagnostics.
Only the user may accept a variant or promote a Selected Baseline.

## Implementation and resolved bring-up faults

The retained source head is
`25157d78f13e4be8215530639b166e772eaadb2c`. One FastRPC invocation owns one
complete block batch. It acquires an exact 8 MiB Prepared Runtime Session,
starts one persistent HMX worker, streams only legal boundary and weight data
with User DMA, and keeps all model intermediates in its VTCM arena. F16F16 and
W4F16 projections use FP16 HMX. W4U8 projections unpack the shared W4 carrier
to S8 and use asymmetric-U8 by S8 integer HMX. In this first block prototype,
QK and AV remain a declared common FP16 HMX attention island; W4U8 converts its
Q/K/V projection outputs inside VTCM before that island. RMSNorm, Q/K norm,
RoPE, causal Softmax, and SiLU-times-Up are scalar reference-quality kernels,
not optimized HVX implementations.

Two bring-up failures established contracts that must not be forgotten.
First, V79 FP16 HMX Crouton activation, weight, and output addresses require
2 KiB alignment, while bias/scale loads require 256-byte alignment. The old
generic 128-byte arena alignment truncated encoded HMX addresses and produced
non-finite values. The final arena enforces and statically audits the required
alignments. Second, QuRT `qurt_sem_init()` initializes its count to one. The
HMX worker handoff requires zero-count `command_ready`, `command_done`, and
`worker_started` semaphores, so the final code uses `qurt_sem_init_val(..., 0)`.
Before formal collection, that fix passed 50 F16F16, 5 W4F16, and 20 W4U8
process-level stress runs without a failure.

## Interpretation

The repeat-one result shows a real cold-block W4U8 benefit: 15.71% lower Host
wall latency than F16F16 while reading approximately one quarter as many
weight bytes. That benefit nearly disappears in repeat-ten steady state, where
W4U8 is only 0.63% faster. At repeat ten, the four projection groups consume
about 1.466 million ticks per F16F16 block but only 0.199 million ticks per
W4U8 block. The roughly 1.267-million-tick projection saving is almost
cancelled by about 1.139 million extra ticks across the current scalar U8
RMSNorm, Q/K norm plus RoPE, FP16 attention-boundary conversion/attention, and
U8 SiLU-times-Up stages. This is direct evidence that the integer-HMX
projection substrate is effective, while the unoptimized non-projection block
path is now the critical limitation.

W4F16 is not a competitive implementation. Its per-channel W4 carrier reduces
weight DDR bytes, but the prototype expands every W4 tile to FP16 with scalar
code before FP16 HMX; Gate/Up and Down dominate roughly 40.2 million repeat-ten
ticks per block by themselves. This variant remains a mathematical control and
negative performance result, not a selected W4A16 baseline.

Execution is complete, evidence is valid, and the local physical and numerical
gates pass. No speed gate was required. Adoption remains pending because only
the user may accept a Project Variant or declare a Selected Baseline.
