# EXP-0085 — GQA-group-major QKV projection scheduling

## Decision and motivation

The user approved EXP-0085 on 2026-08-31 after accepting EXP-0084 as the
unified source parent and promoting its common W4F16 candidate and
EXP-0079-compatible W4U8 path as the fair comparison baselines. The remaining
canonical repeat-ten QKV intervals are about 76,904 ticks for F16F16, 84,009
ticks for W4F16 and 81,518 ticks for W4U8. Qwen3 GQA consumes two Q heads with
one K head and one V head, but the current projection path is organized first
by complete Q, K and V tensors. The experiment tests whether making one GQA
group the outer physical schedule unit reduces boundary handoffs and exposes
useful head readiness earlier.

This is not a change to Q/K/V mathematics and is not an Attention fusion. It
is a storage, command-order and publication experiment below the model layer.
Each logical Linear, head mapping, per-channel W4 scale, activation qparam,
RMSNorm, RoPE, Softmax and AV computation remains unchanged.

## Fixed contract

The Execution Unit is the real Qwen3-1.7B layer-14 complete block at M=64.
F16F16, W4F16 and W4U8 use the accepted EXP-0084 source state, one binary and
their established numerical contracts. Every formal case uses one FastRPC,
exactly 8,388,608 acquired VTCM bytes, one serialized HMX owner, zero
intermediate DDR, zero spill/fill and no QNN. Logical weight bytes and HMX tile
pairs cannot change. Offline packages may contain a group-major copy of the
same Q/K/V values, but model and result artifacts remain on the D drive and
are never committed to Git.

The GQA-Group-Major QKV Super-Projection uses eight outer groups. Each group
contains two 128-channel Q heads, one 128-channel K head and one 128-channel V
head. The candidate presents those four unchanged weight segments in
group-major order, reuses the already-published activation carrier, and
publishes each projected head immediately after its own segment is complete;
it must not wait for the whole group before downstream Norm/RoPE or Attention
can observe readiness.

All three recipes receive the same bounded group-order, prefetch-distance and
publication search where that physical parameter exists. A W4-only mechanism
such as nibble expansion is not imitated on F16F16, but F16F16 still receives
the corresponding storage and command-order opportunity and may not regress.

## Serial milestones

### Stage A — control timeline diagnostic

First add audit-only timestamps to the unchanged EXP-0084 control. For each
GQA group, record activation publication, packed-weight DMA completion, W4
expansion completion where applicable, HMX submission and completion,
individual Q/K/V head publication, and first Attention consumption. The
normal performance mode must not collect this trace. Stage A must identify a
repeated boundary or readiness gap that group-major ordering can actually
remove under one HMX owner. If no such gap exists, implementation stops and
the negative evidence is discussed with the user.

### Stage B — group-major micro gate

Build group-major offline packages and a runtime-selectable candidate. Verify
the physical weight mapping and every Q/K/V head against the independent
reference before running the full block. Candidate and control must have the
same logical values, HMX tile count and numerical output. The micro gate also
checks that per-head publication occurs before whole-group completion and that
no intermediate reaches DDR.

### Stage C — complete block and formal comparison

Run all three recipes from one build at repeat one and repeat ten. W4F16 and
W4U8 must both strictly improve the additive QKV ledger interval and complete
Host wall in ordinary and paired medians at both repeat counts. F16F16 must be
byte-exact, receive the same tuning budget and not regress. A local pass then
requires seven interleaved paired formal rounds, stable device boot, full
PC-027 timing-ledger closure, the PC-028 three-recipe module table, artifact
hashes and physical-contract evidence.

No result becomes a Selected Baseline without another explicit user
promotion.

## Stage A result

Stage A passed on source commit `a54129c3353bb089386f0c1ea5f9ff2e6d89f9eb`.
The retained evidence is
`D:/llm_exp/results/qwen3-block-htp/exp0085/20260830T165254Z_a54129c3353b_stage_a`.
All three controls retained their accepted output hashes and physical gates.
The timeline showed that Q group 7 completed before K group 0 in every recipe,
so the current runtime exposes no K/V head until the complete Q projection has
drained.

| Variant | QKV interval (ticks) | Projection tail (ticks) | Prep tail (ticks) | Post-projection drain (ticks) |
|---|---:|---:|---:|---:|
| F16F16 | 7,563 | 7,554 | 5,973 | 8 |
| W4F16 | 8,548 | 8,046 | 8,523 | 501 |
| W4U8 | 8,207 | 6,863 | 8,177 | 1,341 |

This evidence narrows the hypothesis. Group-major ordering is not expected to
make the serialized HMX projection work itself faster. Its addressable benefit
is earlier K/V publication and overlap of Q/K Norm plus RoPE with the remaining
projection stream, removing the W4 post-projection preparation drain. The
F16F16 path has only eight drain ticks and therefore serves primarily as the
non-regression control in Stage B.

## Stage B result

Stage B used source commit `d2faa44e8c31feb39fc1ebbd344fdaf4c3ed7fed`
and retained evidence at
`D:/llm_exp/results/qwen3-block-htp/exp0085/20260830T172859Z_d2faa44e8c31_stage_b`.
It searched the control, group windows of one, two and four groups, and Q-prefix
values of four and six with the same bounded opportunity for all recipes. All
cases retained the accepted output hash, exact 8 MiB VTCM, zero intermediate
DDR, zero spill/fill, unchanged logical weight bytes and unchanged HMX tile
pairs.

Pure group-major schedules failed on W4U8 because they exposed K early by
delaying the second half of Q. The best compromise was `q_prefix4_k_all`, which
completed the first four Q groups, then all K groups, then the final four Q
groups. Its three-round W4F16 medians improved QKV by 6.42% and Host wall by
1.33%. W4U8 QKV improved by only one tick while Host wall improved 0.95%, so
the apparent W4U8 benefit was too small to accept but sufficient to select the
candidate for the required seven-round formal gate.

## Stage C result and decision

Stage C used source commit `5161d8adb1095f262e58949bf6be6e41523f6afa`.
Formal evidence and retained binaries are respectively:

`D:/llm_exp/results/qwen3-block-htp/exp0085/20260830T173432Z_5161d8adb109_stage_c_formal`

`D:/llm_exp/models/qwen3-block-htp/exp0085/artifacts/5161d8adb109/stage_c_formal`

Seven interleaved paired rounds produced the following medians. Positive values
mean the candidate is faster than the direct EXP-0084 control.

| Variant | Repeat | QKV improvement | Host-wall improvement |
|---|---:|---:|---:|
| F16F16 | 1 | +1.85% | +0.18% |
| F16F16 | 10 | +2.08% | +0.34% |
| W4F16 | 1 | +6.28% | +0.94% |
| W4F16 | 10 | +4.50% | +0.36% |
| W4U8 | 1 | -1.73% | -1.05% |
| W4U8 | 10 | -0.84% | -0.52% |

The paired medians have the same sign in every W4U8 gate cell. Correctness,
physical residency, stable boot, PC-027 timing-ledger closure and the PC-028
three-recipe module table all passed. The local speed gate nevertheless fails
because W4U8 must strictly improve at both repeat counts. EXP-0085 is therefore
rejected as a common schedule, EXP-0084 remains the provisional source parent
and all selected fair baselines remain unchanged. The positive FP16 result is
retained as evidence, not silently adopted as a recipe-specific baseline.
