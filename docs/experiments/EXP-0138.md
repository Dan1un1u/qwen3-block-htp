# EXP-0138 — W4F16 Gate/Up initial Up-DMA overlap

## Decision and hypothesis

EXP-0136 is the latest valid W4F16 local candidate. It uses four expansion
contexts, all four locked pool workers plus the main context for final
Crouton-native SwiGLU drain, and four-tile consumer subgroups. Its steady-state
stream tail is effectively closed, while Gate/Up remains the largest W4F16
module.

The existing Gate/Up startup is unnecessarily serial. It completes the first
Gate weight DMA, completes the first Up weight DMA, submits both next-batch
prefetches, and only then expands the first Gate group. The candidate keeps the
Gate first batch synchronous but submits the Up first batch asynchronously.
While that Up DMA is in flight, it submits the Gate next-batch prefetch and
expands the first Gate group. The first Gate HMX command is then dispatched
before the main context waits for the Up first batch, starts the Up next-batch
prefetch, and expands the first Up group. All later groups retain the existing
interleaved pipeline.

The hypothesis is that overlapping the compulsory Up startup transfer with
Gate expansion and the first Gate HMX command removes a one-time startup
interval without perturbing the balanced steady-state schedule.

## Gates

The control is the complete EXP-0136 four-tile-subgroup plan. The candidate
changes only the initial Up batch DMA from synchronous completion to the same
existing asynchronous prefetch descriptor used by later batches. Gate and Up
weight values, scales, FP16 activation, W4-to-FP16 expansion, DMA bytes and
descriptor count, HMX batch-eight commands and tile work, Crouton carriers,
worker creation and assignments, four-tile SwiGLU subgroups, Down, Attention,
residuals, Public Common Layer, and numerical output remain fixed.

Static evidence must prove that the Up initial transfer is started before Gate
group-zero expansion, that Gate HMX group zero starts before Up initial-DMA
completion is awaited, and that no Up expansion or HMX command reads the buffer
before completion. Both cells must produce byte-exact output
`f18b9abbe1487231`, pass the W4F16 expansion audit, request exact 8 MiB VTCM,
retain zero intermediate DDR and spill/fill, one FastRPC Execution Unit, one
HMX owner, no QNN, and identical weight bytes, DMA descriptors, HMX commands,
tile work, carriers, and peak VTCM plan. Declared DMA ordering and lifetime
telemetry may differ.

The candidate passes only if Gate/Up plus SwiGLU and complete Host wall
strictly improve in ordinary and paired repeat-one and repeat-ten medians over
five rotated rounds. PC-027 and PC-028 are mandatory. A local pass remains
pending user decision and cannot promote a Selected Baseline automatically.

Both cells produced byte-exact output `f18b9abbe1487231`, zero W4F16 expansion
mismatches, and zero maximum LSB error. The physical contract passed with an
exact 8 MiB VTCM grant, zero intermediate DDR and spill/fill, one FastRPC
Execution Unit, one HMX owner, no QNN, and identical weight bytes, DMA
descriptors, HMX commands and tile work, carriers, and peak VTCM plan. Dynamic
telemetry proved that every candidate block submitted the first Gate HMX
command before awaiting completion of the first Up weight DMA.

The new ordering lowered repeat-ten stream-ready wait by 6.930% (7.278%
paired), but increased stream-join wait by 33.835% (51.807% paired). Gate/Up
changed by only -0.020% (-0.111% paired) at repeat one and -0.174% (-0.192%
paired) at repeat ten. Complete Host changed by -0.319% but +0.063% paired at
repeat one, and regressed 0.005% in both ordinary and paired repeat-ten
medians. The required four-way speed gate therefore failed.

The control remains selected and EXP-0138 is rejected. Reopening requires a
single DMA-chain or shared-completion contract that transfers the ready Up
batch without introducing another main-context wait or join tail; merely
moving the existing wait is not a new hypothesis.
