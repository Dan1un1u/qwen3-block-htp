# EXP-0084 — Cross-recipe common-schedule parity backports

## Decision and motivation

The user approved this experiment on 2026-08-30 after identifying that the
current F16F16, W4F16 and W4U8 headline comparison mixes quantization effects
with unequal optimization maturity. The existing table is useful as a
current-best engineering status, but it is not sufficient evidence for the
causal speed effect of one numerical recipe.

EXP-0084 pauses W4U8-only optimization and backports only scheduling ideas
whose physical meaning exists on the FP16 activation paths. It then measures
all three recipes from one source commit and one binary. Rejected W4U8
experiments are not inherited. EXP-0079 supplies the unchanged W4U8 control;
EXP-0038 supplies the selected W4F16 contract and the fastest valid paired
F16F16 control.

## Fixed physical and numerical contract

The Execution Unit is the real Qwen3-1.7B layer-14 complete block at M=64.
Every formal run uses one FastRPC invocation, exactly 8,388,608 acquired VTCM
bytes, one HMX owner, zero intermediate DDR, zero spill/fill and no QNN or
QAIRT path. Weight values, per-channel W4 scales, activation values, FP16
RMSNorm/RoPE/Softmax/SiLU mathematics, U8 qparams, integer Attention and all
tensor boundaries remain fixed unless the milestone explicitly changes only
the task topology used to produce the same bytes.

F16F16 and W4F16 receive the same candidate grid, sample count, selection
rule and repeat-one/repeat-ten gate. A shared optimization may be called
common only if it is byte-exact and non-regressing for both FP16 recipes.
Recipe-specific best plans may still differ after equal-budget tuning, but
that distinction must remain visible in the final report.

## Serial milestones

### Stage A — FP16 Q/K Norm-RoPE head pairs

Replace the current sixteen independent Q-head tasks plus eight independent
K-head tasks with eight Q-pair tasks plus four K-pair tasks. Reuse invariant
gamma, RoPE table and loop state while preserving the complete computation of
each head. Projection commands, Q/K readiness generations, GQA Attention,
standard stable FP16 Softmax and all HMX scheduling remain unchanged.

The gate requires byte-exact output and strict non-regression of Q/K-prep
work, the complete QKV ledger interval and Host wall for both F16F16 and
W4F16 at repeat one and repeat ten.

### Stage B — FP16 Input RMSNorm persistent-pool rows

Partition the existing FP16 Input RMSNorm into disjoint row tasks executed by
the already-created persistent HVX pool. Each row retains the existing
reduction order, reciprocal square root, gamma multiplication and selected
Crouton-native output contract. The bounded worker grid is identical for
F16F16 and W4F16.

The gate requires byte-exact output and non-regression of Input RMSNorm,
Input-Norm-plus-QKV and Host wall for both recipes at both repeat counts.

### Stage C — FP16 Post-residual plus RMSNorm persistent-pool rows

Apply the same row-task principle to the fused post-Attention residual and
RMSNorm boundary. Final residual remains unchanged because the current FP16
implementation is already materially faster than W4U8 and has no matching
optimization deficit.

The gate requires byte-exact output and non-regression of the complete
post-residual/norm-plus-Gate/Up boundary and Host wall for both FP16 recipes at
both repeat counts.

### Final synchronized comparison

Run F16F16, W4F16 and unchanged EXP-0079 W4U8 from one source commit and one
binary on one stable boot in interleaved order. Report both the common
canonical schedule and each recipe's best plan selected from equal search
budgets. PC-027 and PC-028 closure is mandatory. No result becomes a Selected
Baseline without explicit user promotion.

## Implementation and formal result

The source implementation is retained on
`codex/exp-0084-cross-recipe-common-schedule-parity` at
`6dc437fe08eaccf119c4cbce82937e22f125da0b`. It adds runtime-selectable FP16
Q/K head pairing and two row-task persistent-pool RMSNorm schedules, together
with explicit task/work/wait telemetry. W4U8 takes the unchanged EXP-0079
schedule and byte path. The final formal evidence is:

`D:/llm_exp/results/qwen3-block-htp/exp0084/20260830T160259Z_6dc437fe08ea_formal`

The formal run used one source commit and one built binary, stayed on boot ID
`77ccafe0-8817-4976-bdae-15af5608d4ff`, acquired exactly 8 MiB VTCM, and
reported zero intermediate DDR traffic and zero spill/fill for all three
recipes. All correctness cases retained their established output hashes with
zero mismatches and zero max LSB: F16F16 `704252c89780e695`, W4F16
`f18b9abbe1487231`, and W4U8 `69f22eeb035e5ec5`.

The identical 3x3 grid covered rows per task in `{2,4,8}` and active contexts
in `{2,3,4}` for both FP16 recipes. The common minimax rule selected four rows
and three contexts. Under the same search budget, F16F16 selected 2/4 as its
recipe-specific optimum, while W4F16 selected 4/3. The final collection then
ran two separate seven-round matrices on the same boot. The canonical matrix
uses common 4/3 for both FP16 recipes; the recipe-best matrix uses 2/4 for
F16F16 and 4/3 for W4F16. In each round the three recipes and two matrices are
rotated in order, so W4U8 is not measured only after the FP16 variants.

## Stage decisions

Stage A is rejected. Pairing two Q/K heads per task remained byte-exact, but
W4F16 repeat-ten Q/K pool wait rose from 2,983 to 4,333 ticks, or 45.3%, and
complete Host wall regressed. W4F16 projection overlap often exposes only one
ready head at a time, so waiting for the second head delays useful work. This
is an A8-compatible idea that is not a valid cross-recipe common schedule.

Stage B passes. The FP16 Input RMSNorm persistent pool reduces the repeat-ten
Input RMSNorm ledger by about 59.5% for both F16F16 and W4F16 and does not
regress either recipe's complete Host wall at repeat one or repeat ten. Stage
C also passes: the post-Attention residual-plus-RMSNorm interval falls by
about 59.5% for both recipes with non-regressing Host wall at both repeat
counts.

The combined B+C candidate passes all four common Host-wall cells. F16F16
changes from 2,914.271 to 2,844.323 microseconds at repeat one and from
2,487.547 to 2,453.141 microseconds per block at repeat ten. W4F16 changes
from 2,656.094 to 2,609.115 microseconds at repeat one and from 2,213.479 to
2,165.375 microseconds per block at repeat ten. The corresponding repeat-ten
latency reductions are 1.38% and 2.17%.

## Fair three-recipe comparison

The canonical repeat-ten Host-wall medians are 2,442.370 microseconds for
F16F16, 2,161.776 microseconds for W4F16 and 1,955.276 microseconds for the
unchanged W4U8 plan. W4F16 is 13.0% faster than F16F16, while W4U8 is 10.6%
faster than W4F16. The equal-budget recipe-best matrix measures 2,436.417,
2,162.021 and 1,948.313 microseconds respectively; W4U8 is 11.0% faster than
W4F16. The small difference between the two W4U8 medians is normal run-order
variation because its code and schedule are identical in both matrices.

The prior current-best comparison used the older selected W4F16 result and
showed a 14.1% W4U8 advantage. After backporting the physically applicable
persistent-pool lifecycle work and giving both FP16 recipes the same search
budget, that advantage becomes 10.6% to 11.0%. Thus roughly 3.1 to 3.5
percentage points of the earlier apparent A8 benefit came from unequal
optimization maturity rather than activation precision itself. This confirms
the user's fairness concern quantitatively.

The module table also shows that the remaining W4U8 advantage is not uniform.
Depending on canonical versus recipe-best sampling, Gate/Up plus SwiGLU is
40.6% to 42.2% faster than W4F16, whereas Input RMSNorm is about 9% slower,
integer QK-Softmax-AV is about 29% slower, and the residual/nonlinear
boundaries remain substantially slower. The W4U8 overall win is therefore a
projection-dominated balance, not evidence that every A8 operator is faster.

PC-027 and PC-028 are complete in `full_profiling_report.md`; the evidence
checksums validate. Local gate is pass, but adoption remains pending. Neither
the selected W4F16 baseline nor the selected W4U8 baseline is changed without
an explicit user promotion decision.
